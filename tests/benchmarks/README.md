# Mixed-library benchmark

`run_mixed.py` measures the mixed-library fixture generated by `tests/fixtures/mixed_library/generate.py`.

```bash
python tests/fixtures/mixed_library/generate.py --root /tmp/zimantic-mixed --force
python tests/fixtures/mixed_library/kiwix_server.py --port 8085 &
python tests/benchmarks/run_mixed.py --root /tmp/zimantic-mixed \
    --build full \
    --device-model "Raspberry Pi 4 Model B 4 GB" --ram 4GB \
    --os "Raspberry Pi OS 64-bit" --storage "USB SSD" \
    --commit "$(git rev-parse --short HEAD)" \
    --fixture-revision phase09-v1 \
    --json-out tests/benchmarks/results/pi4-phase09.json \
    --markdown-out tests/benchmarks/results/pi4-phase09.md
```

The report contains:

- startup time until `/health` is ready with local Kiwix available;
- cold and warm build times for the 1,000-file tree and Kolibri channel (run `--build` twice);
- search p50/p95 after one warm-up request over the fixed 100-query set;
- `/library` payload size and render time;
- peak process RSS (`VmHWM`) after the server handles search requests;
- a ZIM-only and mixed-library `/search` comparison with the same query file.

The benchmark measures ZIM, Files, and Kolibri providers together. It requires the documented fixture and query set. Result files are local artifacts; `tests/benchmarks/results/` is gitignored and is not retained in the repository. A missing Raspberry Pi 4 result is unverified.

`scripts/benchmark_body_fts.py` provides a synthetic comparison. It does not replace a measurement with the real providers.

## HTML parsing

`run_html.py` compares the stdlib streaming parser, the production Lexbor extractor, lxml's streaming target and DOM, and Beautiful Soup + lxml. Each parser uses the same text-selection rules. Comparison-only dependencies are not application requirements:

```sh
uv run --with lxml --with beautifulsoup4 python tests/benchmarks/run_html.py \
    --zim zims/wikipedia_en_100_2026-08.zim --module modules/en-olpc \
    --pages 12 --repeats 5 --output /tmp/zimantic-html
```

The output includes repeated body and preview timings, exact-output agreement, empty-result regressions, fresh-process native-memory probes, and blinded review samples with source HTML. Record preferences before you open `review-key.json`. Archive decompression and file I/O are excluded.

See [the November 7 results](results/html-parsers-2026-11-07.json) and [quality/memory caveats](../../docs/build-performance.md#html-parser-comparison-november-7-2026).

## Native-search worker budgets

`run_native.py` compares 1, 2, 4, 8, and automatically budgeted helpers under transient `systemd-run --user` services. A working systemd user manager with CPU and memory controllers is required; it does not require root:

```sh
uv run python tests/benchmarks/run_native.py \
    zims/wikipedia_en_top_mini_2026-09.zim \
    zims/wikipedia_en_geography_maxi_2026-07.zim \
    zims/wikisource_en_all_nopic_2026-09.zim \
    zims/libretexts.org_en_stats_2026-01.zim \
    --legacy --output tests/benchmarks/results/native-workers.json
```

`--limits` accepts CPU-quota:RAM-MiB pairs, such as `1:512 2:1024`. Each trial limits CPU time, sets `MemoryMax` and `MemorySwapMax=0`, disables core dumps, and limits service runtime to 90 seconds. `--legacy` also measures two helpers per collection, reproducing the per-collection multiplicative budget. Trials run sequentially and their transient units are collected.

The fixed 12-query mix has a 16-hit limit, eight source threads, one 96-search warm-up and 96 measured searches, with two fresh-service trials per configuration. `--workers`, `--source-workers`, `--requests`, and `--repeats` are adjustable. `--resident-mib 256` touches and retains a 256 MiB allocation after it resolves the automatic budget, simulating server/model residency. Reports preserve observed cgroup CPU/RAM budgets, search throughput/p50/p95, CPU throttling, cgroup memory peaks and OOM counters, sampled process-tree PSS, failures, and exact-result digest agreement. Durations include backend queue waits but not time queued in the source executor.

Use `--backends processes threads --min-seconds 3` with a GIL-releasing binding to compare both backends. The minimum duration repeats the same measured query batch, checks result agreement between batches, and reports total requests, CPU milliseconds per request, and average utilized CPU cores. Run several fresh-service repetitions. `PYTHONPATH` and `LD_LIBRARY_PATH` are forwarded explicitly into the transient service, so local binding/native builds also reach process helpers. The report records native dependency versions and the loaded binding path; different dependency versions are a version-comparison caveat, not evidence of a pure GIL speedup.

For a four-core/2 GiB resource proxy use `--limits 4:2048`; for this 20-thread desktop with a safety memory limit use `--limits 20:8192`. Add `--resident-mib 512` to retain the same simulated server/model headroom in both profiles. CPUQuota counts CPU time, not Pi instruction speed: neither this nor MemoryMax emulates ARM cores, Pi storage, or whole-server work.

These are ZIM full-text microbenchmarks, not whole-server memory or Raspberry Pi performance guarantees. They do not load models/FAISS or hydrate previews. OS caches stay warm: the harness never drops shared host caches, and cached file pages can be charged outside the service's cgroup. MemoryMax therefore tests cgroup-accounted memory pressure, not every physical page used by the ZIM file. PSS is reported separately.

Regenerate the native-only matrix, resident-headroom matrix, and short failure-report validation with the commands below; their JSON files are local artifacts and are not retained in the repository. See the [interpretation and limit audit](../../docs/architecture.md#constrained-workerbudget-comparison-november-8-2026). The native-only matrix records a four-helper automatic ceiling; the headroom matrix uses an eight-helper ceiling.

### Reader GIL/thread results, November 9, 2026

The 81-trial report (regenerate with the command below) preserves original installed-stack baselines, controlled original-reader baselines on the same native dependencies, the process/thread matrix, and four-source-thread Pi-budget confirmation. Summaries are medians of three fresh-service trials. Absolute binding paths are removed; source revisions and native dependency versions identify each stack. The installed distribution version can differ from a locally overridden binding.

The main measured-stack command is:

```sh
uv run python tests/benchmarks/run_native.py \
    evaluation.zims/wikipedia_en_astronomy_maxi_2025-11.zim \
    evaluation.zims/wikipedia_en_medicine_maxi_2026-04.zim \
    evaluation.zims/cooking.stackexchange.com_en_all_2026-07.zim \
    --workers 1 2 4 8 --backends processes threads \
    --limits 20:8192 4:2048 --repeats 3 --requests 144 \
    --min-seconds 3 --source-workers 8 --resident-mib 512 \
    --output tests/benchmarks/results/native-threads-local.json
```

Set `PYTHONPATH` to the built reader-binding directory and `LD_LIBRARY_PATH` to the patched native library and its dependencies before you invoke the runner. The controlled baseline exports zimantic `cb261c5`, copies this same runner into it, and uses a python-libzim `57555c2` build linked against that identical native stack. It runs only `--backends processes`, with `--workers 4 8`; other main-matrix options are the same. The Pi-budget confirmation uses `--workers 4 --limits 4:2048 --source-workers 4` for both the controlled baseline and GIL-releasing backends.

The [analysis and ZIM full-text search profile overrides](../../docs/architecture.md#reader-gilthread-comparison-november-9-2026) separate snippet suppression from threading gains and describe resource, memory-accounting, and whole-server limitations.

## Fetching snippets during search

`run_snippets.py` compares deferred previews with native snippets or identical HTML leads prefetched for the first N candidates per source:

```sh
uv run python tests/benchmarks/run_snippets.py \
    evaluation.zims/wikipedia_en_astronomy_maxi_2025-11.zim \
    evaluation.zims/wikipedia_en_medicine_maxi_2026-04.zim \
    evaluation.zims/cooking.stackexchange.com_en_all_2026-07.zim \
    --strategies deferred native:4 native:16 lead:4 \
    --limits 4:2048 --repeats 3 --requests 24 --min-seconds 2 \
    --output tests/benchmarks/results/snippets-single-client-2026-11-09.json
```

Set `PYTHONPATH` and `LD_LIBRARY_PATH` to the patched binding/native builds as above. Both backends need snippet suppression; threads additionally require the native mutex fix. This runner does not affect production search behavior. `deferred` uses the production `FulltextPool`; the eager variants replace only its worker cache/entry point, retaining its scheduling and JSON IPC.

Every query searches all supplied ZIM files for 16 candidates each, ranks with the production ranker, then hydrates only the displayed ten. `native:N` keeps libzim's query-centered snippets and falls back to the normal limited reader for displayed results without one. `lead:N` uses that same reader in the search worker, preserving the existing opening-text preview. Native snippets are normally about 500 characters, versus the configured 1,000-character lead; they are not equivalent text or UX. Zimantic strips native `<b>` highlighting before reuse as plain text.

Both `--cache miss hit` cases bypass finalized-query caching. Misses disable preview reuse; hits prepopulate every displayed path with a normal, query-independent lead. This isolates expensive preview misses from searches whose paths are already cached. It is not a prediction of the real hit rate. The same limited source executor handles source search and deferred hydration. Default trials retain 512 MiB of simulated server/model headroom.

Reports include end-to-end and pre-hydration p50/p95, CPU/query, throughput, prefetch generation/reuse/waste, fallback reads, cache hits, preview lengths, text samples, cgroup accounting and sampled process-tree PSS. All repeated batches and strategies preserve exact candidates and ranked identities; `lead:N`, deferred previews, and all warm-cache cases also return identical preview text. Query latency includes source/native queue waits, not time queued in the client executor.

For four concurrent uncached queries on this desktop, use `--clients 4 --workers 8 --source-workers 8 --limits 20:8192 --cache miss --requests 48`. Also repeat with one ZIM file: a selective-prefetch win from overlapping work across several sources need not survive a single-source search. These are native-only search/preview pipeline measurements: no model, SQLite title/body channels, phrase enrichment, HTTP, or whole-server startup. Shared host caches are never dropped; CPU quotas do not emulate Pi hardware.

See the [75-trial results and recommendation](../../docs/architecture.md#snippet-prefetch-comparison-november-9-2026).

## Derived-text worker pool

`run_derived.py` measures the process pool used for OCR, ASR, and embedded
caption extraction. It runs the committed Tesseract fixture sequentially and
through increasing pool sizes, and checks that every configuration returns the
same text digest.

```sh
uv run python tests/benchmarks/run_derived.py \
    --count 32 --repeats 5 --workers 2,4,8 \
    --json-out tests/benchmarks/results/derived-workers-2026-11-11.json
```

The November 11, 2026 desktop run (20 logical CPUs, Tesseract `eng`, 32 OCR
tasks) measured 1.97 s sequential, 1.11 s with two workers (1.77×), 0.65 s with
four (3.04×), and 0.46 s with eight (4.30×). All runs produced the same text
digest. This measures engine dispatch only. The production pool is shared by
concurrent source builds; a single source still reads and extracts its entries
sequentially. Do not treat the synthetic speedup as a whole-build prediction.
